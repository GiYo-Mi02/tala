# Phase 2.3 verification website handoff

Phase 2.2 sends accepted scans and structured values to the existing intake API. The website can consume them from the same versioned backend at `/api/v1`. Use the [OpenAPI contract](../phase-2.1/openapi.json) for payloads and errors.

1. Use an approved **VERIFIER** account. Use HTTPS and register the website origin in `CORS_ORIGINS`. Browser `POST /auth/login` uses `mode: "browser"`. Retain the bearer access token in memory, use credentialed browser refresh and logout with the secure, HTTP-only cookie, and use `GET /auth/me` to confirm the role. Plan a same-site deployment so the strict refresh cookie works.
2. Use `GET /verification/queue` to list pending submissions and the in-review filter when needed. Use the pagination values `limit`, `offset`, and `nextOffset`. The encoder enters this queue only after validated completion. `GET /submissions/{id}` provides the latest status, reviewer, revision, receipt, pages, field values, and verifier history.
3. Load the exact template mapping with `GET /templates/{id}/versions/{version}`. Render the fields by template ID, field key, display order, and page number. Use authenticated requests for `GET /submissions/{id}/pages/{pageNumber}`. Create a short-lived browser object URL for the fetched image, revoke it when the view closes, and keep scans out of service worker caches, analytics, or public paths.
4. Present the raw OCR reading, confidence and regions where available, mobile-confirmed value, latest verifier correction, and frozen final value separately. Original OCR and confirmed evidence are immutable. Render absent readings and blanks according to the versioned template. Treat verification as a human action.
5. Use `POST /submissions/{id}/review/claim`, then the assigned-verifier endpoints for `correct`, `verify`, `return`, `reject`, and `finalize`. Send a fresh UUID per logical action in `Idempotency-Key` and the latest quoted revision from `ETag` in `If-Match`. After a lost response retry the same action and key. On HTTP 412, reread the record before retrying with revised input. Return and reject require a reason, and finalization requires prior verification.
6. Communicate review state alongside the receipt. `PENDING_VERIFICATION`, `IN_REVIEW`, `NEEDS_CORRECTION`, `VERIFIED`, `REJECTED`, and `FINALIZED` describe verifier progress. A mobile synchronization receipt describes delivery. An expired incomplete intake is outside the review queue.

The Phase 2.2 host integration test retrieved a fictional two-page record with verifier credentials, returned it for correction, and confirmed that the encoder could retrieve the new decision alongside the original receipt. Physical-phone and website acceptance are separate from that test. See [Phase 2.2 acceptance](acceptance.md).
