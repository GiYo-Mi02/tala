# Phase 2.2 investigation

The existing Android scanner is an Expo 54 and React Native application. Its CameraX, OpenCV, and bundled ML Kit OCR run in the Android `tala-ocr` module. BEEF and SSS E-1 drafts live as JSON in the `drafts` and `fixed_form_drafts` tables of `tala-phase1.db`. Accepted JPEG files and historical field evidence are app-private. Each draft and accepted image has a UUID. Both review screens can save a complete draft locally. Those actions are independent of networking.

BEEF version 1 requires pages 1 and 2 and seven confirmed fields. Its field OCR records use `ocrHistory`, `RawField.text`, and optional split regions. SSS E-1 version 1 captures page 1 and conditionally page 3. Page 2 is reference material. It has conditional fields and manual controls. Its per-page `history` records store selected raw text, supported confidence, and an image-relative rectangle. Both formats retain confirmed values separately from raw evidence.

The inspected [OpenAPI 3.1 document](../phase-2.1/openapi.json) and [Express implementation](../../apps/backend/src/app.ts) agree on native login, refresh, logout, account details, encoder intake, binary page uploads, fields, completion, and progress/status reads. Each intake mutation uses a UUID idempotency key. Submitted page slots bind a client image UUID and SHA-256 digest. The API requires the complete confirmed field snapshot and stores a receipt only after eligible pages and fields commit. The server can return a newer verification state alongside the original receipt. PostgreSQL constrains the owner and client UUID, template version, page slots, field keys, and OCR image references in the existing [migration](../../apps/backend/migrations/0001_foundation.sql). The private storage adapter validates and stores image bytes outside HTTP static routes.

The last Phase 2.1 run recorded 14 passing test results, including 9 HTTP and PostgreSQL integration cases. The log showed interrupted upload recovery, idempotency, field rollback, separate OCR and corrected values, cookie and token checks, private image access, and stable receipt retrieval. The API provides the necessary endpoints. Phase 2.2 can use the existing database schema and server implementation.

The local draft profile is synthetic and has no backend account identity. Phase 2.2 binds the explicitly queued snapshot to the signed-in encoder and API endpoint. Expo's draft database depends on the React Native module context. The worker uses a separate Room SQLite outbox so it can start independently and avoid sharing a database file across SQLite runtimes. The existing draft and OCR repositories keep their formats and offline behavior.
